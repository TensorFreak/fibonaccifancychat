Вердикт
Ядро распределённой логики — крепкое и проверено (идемпотентность на БД, FIFO-порядок, resumable-стриминг, мультиинстанс, миграции, пагинация). Но как прод-сервис в текущем виде НЕ готов: не хватает «операционного кольца» — безопасных дефолтов, границ ресурсов, таймаутов, неблокирующего auth, наблюдаемости. Есть несколько CRITICAL, которые я бы считал блокерами.

🔴 CRITICAL (блокеры go-live)
1. Небезопасные дефолты аутентификации. config.py:65,71

auth_secret = "dev-insecure-change-me" — если забыть переопределить в проде, любой может подписать JWT на любой user_id → полный захват аккаунтов и доступ ко всем диалогам.
auth_dev_mode = True по умолчанию — если не выставить false, любая строка-токен принимается как личность (authenticate → uuid5), auth фактически выключен.
Нет старт-гарда, который бы отказался подниматься с дефолтным секретом при auth_dev_mode=false. → Секьюрность зависит от того, что оператор не забыл две переменные. Нужно: fail-fast при старте (нет секрета / дефолтный секрет в прод-режиме) и auth_dev_mode=False по умолчанию.
2. Redis-стримы растут безгранично → OOM. chat:inbound, chat:summarize
XACK убирает запись из PEL, но не из стрима. XADD без MAXLEN/XTRIM (api/main.py:308, llm_worker.py:237) → каждое сообщение за всё время остаётся в Redis навсегда. За недели прод-трафика Redis упрётся в память и ляжет. (gen:-ленты живут по TTL — они ок.) Нужно XADD … MAXLEN ~ N или периодический XTRIM MINID.

3. У вызова LLM нет таймаута. llm/client.py:22 — httpx.Timeout(None)
Зависшее соединение с моделью блокирует воркер навсегда и стопорит FIFO-гейт этого диалога. При этом замок диалога ex=120 истечёт, а генерация всё ещё идёт → второй воркер (reclaim) начнёт дублирующую генерацию. Нужны разумные connect/read/total-таймауты.

4. «Настоящего» прод-auth нет — это скелет. auth.py
JWT на общем секрете + dev-фолбэк. Нет: сброса пароля, верификации email, отзыва/blacklist токенов (JWT живёт 7 дней и неотзываем), рейтлимита, корп-SSO. Для внутреннего теста ок; для корпоративного прод-сервиса — обязательна интеграция вашего SSO/OIDC.

🟠 HIGH
5. bcrypt блокирует event loop. auth.py:24,28 — hash_password/verify_password синхронные (~100 мс CPU), вызываются прямо в async register/login (api/main.py:85,94). Всплеск логинов сериализуется и тормозит весь api-инстанс. → asyncio.to_thread.

6. Бесконечный re-enqueue в FIFO-гейте. llm_worker.py:155
Если номер seq «израсходован», но сообщение не дошло (api сделал INCR, а XADD упал), все последующие сообщения диалога бесконечно крутятся (≈20 XADD/с) → диалог навсегда завис + мусор в стриме. Нет предела попыток / dead-letter / детекции разрыва.

7. TTL замка (120с) не переживает долгую генерацию. llm_worker.py:176 — ex=120 захардкожен. Генерация на большом 256k-контексте может идти дольше → замок истечёт на лету → параллельная обработка/дубль-генерация. Нужен настраиваемый TTL ≫ макс. времени ответа + heartbeat замка.

8. Рейтлимита нет нигде. /api/register,/api/login (перебор паролей), поток сообщений в вебсокете, безлимитное создание диалогов (подключение к /ws/{random-uuid} создаёт диалог). DoS + credential stuffing.

9. Pub/Sub не переживает рестарт Redis. api/main.py:271 — при failover/рестарте Redis pubsub.listen() упадёт, pump_out умрёт, и уже открытые сокеты тихо перестанут получать события (токены-то из durable-ленты, а вот user_message/gen_start — нет) до реконнекта клиента. Нет resubscribe-логики.

🟡 MEDIUM
10. LLM-клиент создаёт новый httpx.AsyncClient на каждый вызов (нет keep-alive), и нет ретраев с backoff на 429/5xx — при лимитах модели восстановление медленное. llm/client.py:22
11. load_messages_since грузит весь несвёрнутый хвост без лимита — если суммаризатор отставал, риск OOM. db.py:217
12. Соединения Postgres: (api+worker+summarizer)×10 против дефолтных max_connections=100 — при масштабировании нужен PgBouncer (уже в docs/12).
13. У суммаризатора нет reclaim PEL — умерший суммаризатор бросает задачу (само-лечится на следующем триггере, но запись висит в PEL).
14. Логи — print(). Нет структурированных логов, уровней, correlation-id → тяжело эксплуатировать.
15. Наблюдаемости нет: метрик нет, /healthz не проверяет зависимости (это liveness, не readiness).
16. Пароль >72 байт → bcrypt кинет ValueError → 500 на регистрации (не обработано). auth.py:24
17. Контейнер работает от root, в Dockerfile нет HEALTHCHECK, uvicorn без --proxy-headers (за прокси).
18. Нет закоммиченного набора тестов/CI — вся проверка шла ад-хок; для прода нужен автотест-набор в пайплайне.
🟢 Что реально крепко (не переделывать)
Идемпотентность вставок — INSERT … ON CONFLICT по (message_id, role), без окна потери.
FIFO-порядок при N воркерах — гейт по seq + перепроверка под замком.
Resumable-стриминг и мультиинстанс — durable-лента + active_gen, без sticky-сессий.
Контроль длины промпта — реальный потолок под окно модели.
Миграции — advisory-lock, безопасны при параллельном старте.
Пагинация — keyset без OFFSET, устойчива к вставкам.
XSS: клиент рендерит через textContent — инъекций нет.
Рекомендованный порядок до go-live
Секьюрность-дефолты (#1): fail-fast без секрета, auth_dev_mode=False по умолчанию.
Границы ресурсов: MAXLEN на стримы (#2), таймауты LLM (#3), лимит в load_messages_since (#11).
Event-loop: bcrypt в threadpool (#5).
Живучесть: предел re-enqueue/dead-letter (#6), TTL замка под длинную генерацию (#7), resubscribe Pub/Sub (#9).
Anti-abuse: рейтлимит на auth и ws (#8).
Эксплуатация: структурные логи + метрики (#14,15), non-root контейнер (#17), тест-набор в CI (#18).
Auth: интеграция вашего корп-SSO (#4).
