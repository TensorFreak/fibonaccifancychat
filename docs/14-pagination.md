# 14. Пагинация: два курсора

**Код:** [`app/db.py`](../app/db.py) (`load_messages_page`, `list_conversations_page`) ·
[`app/api/main.py`](../app/api/main.py) (эндпоинты + курсоры)

Для больших объёмов используется **keyset-пагинация** (курсоры), а не `LIMIT/OFFSET`.
Причина: `OFFSET` на глубоких страницах сканирует и выбрасывает все пропускаемые строки
(O(offset)), а keyset идёт прямо к нужному месту по индексу (O(log n + limit)) и
устойчив к вставкам между запросами (нет «съезда» страниц).

## message_cursor — сообщения внутри чата (прокрутка вверх)

Листаем историю потенциально длинного чата к более старым сообщениям.

- **Ключ сортировки:** `messages.id` (монотонный `BIGINT`), индекс `(conversation_id, id)`.
- **Курсор:** `before` — id, строго **старше** которого грузим.
- **Эндпоинт:** `GET /api/conversations/{id}/messages?before=<id>&limit=<n>`
  - без `before` → последняя (самая свежая) страница;
  - ответ: `{messages: [{id, role, content}], next_cursor, has_more}`;
  - `messages` — в **хронологическом** порядке (старые слева), готовы к рендеру;
  - `next_cursor` — id самого старого сообщения страницы; передать в `?before=` для
    следующей (более старой) страницы; `null`, когда старее нет.

```sql
SELECT id, role, content FROM messages
WHERE conversation_id = $1 AND id < $before      -- $before опускается на первой странице
ORDER BY id DESC LIMIT $limit + 1                 -- +1, чтобы вычислить has_more
```

Клиент ([`chat.html`](../app/static/chat.html)) подгружает старые при прокрутке к верху
`#log`, вставляет их блоком сверху и сохраняет визуальную позицию.

## chat_cursor — список диалогов (до самых старых)

Листаем список чатов пользователя вглубь истории.

- **Ключ сортировки:** `(created_at DESC, id DESC)`. `id` — вторым ключом, чтобы разрешать
  коллизии одинаковых `created_at` (иначе на границе можно потерять/задвоить строку).
- **Индекс:** `idx_conversations_user_created (user_id, created_at DESC, id DESC)`
  (миграция `0002`).
- **Курсор:** непрозрачный токен = base64 от `(created_at, id)` последней показанной строки.
- **Эндпоинт:** `GET /api/conversations?cursor=<token>&limit=<n>`
  - без `cursor` → первая (самая свежая) страница;
  - ответ: `{conversations: [{id, title, created_at}...], next_cursor, has_more}`
    (`title` = `null`, пока авто-название не сгенерировано — клиент показывает «Новый чат»,
    `created_at` — для группировки в сайдбаре по датам);
  - `next_cursor` — токен для следующей (более старой) страницы; `null`, когда старее нет.

Сайдбар в [`chat.html`](../app/static/chat.html) рендерит этот список с группировкой по
датам (Сегодня / Вчера / …) и подгружает старые кнопкой «Показать ещё» по `next_cursor`.

```sql
SELECT id, created_at FROM conversations
WHERE user_id = $1 AND (created_at, id) < ($ts, $id)   -- условие опускается на 1-й странице
ORDER BY created_at DESC, id DESC LIMIT $limit + 1
```

Токен курсора кодируется/декодируется в api (`_encode_chat_cursor`/`_decode_chat_cursor`),
клиенту детали не видны — он лишь прокидывает `next_cursor` обратно в `?cursor=`.

## Общие детали

- **`has_more`** вычисляется приёмом «взять `limit + 1`»: если пришла лишняя строка —
  есть ещё страница, лишнюю обрезаем.
- **Размеры страниц** — в конфиге: `messages_page_size` (40), `conversations_page_size`
  (30), верхний предел `page_size_max` (100). `limit` из запроса зажимается в `[1, max]`.
- **Стабильность под нагрузкой:** новые сообщения/диалоги, появившиеся во время листания,
  не ломают курсор — keyset привязан к конкретным `id`/`(created_at,id)`, а не к смещению.

## Проверено

- **chat_cursor:** 7 диалогов, `limit=3` → 3 страницы, порядок свежие→старые, полнота,
  без дублей между страницами.
- **message_cursor:** 10 сообщений, `limit=3` → 4 страницы, склейка `m0..m9` в правильном
  порядке, без дублей и пропусков по `id`.
