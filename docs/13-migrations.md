# 13. Миграции БД

**Файлы:** [`migrations/`](../migrations) · [`app/migrate.py`](../app/migrate.py)

## Зачем

Схема БД эволюционирует (мы уже добавляли `summary_upto_id`, `message_id`, индексы под
пагинацию). На проде с данными нельзя пересоздавать БД — нужен предсказуемый, повторяемый
способ накатывать изменения. Раньше схема грузилась через `schema.sql` только на **чистой**
БД (initdb), что для эволюции не годится. Теперь источник истины схемы — каталог
`migrations/`, а применяет их лёгкий раннер.

## Как устроено

- **`migrations/NNNN_name.sql`** — по одному файлу на изменение, применяются строго по
  имени (`0001_init`, `0002_conversations_pagination`, …). `0001_init` — вся базовая схема
  (идемпотентна: `CREATE … IF NOT EXISTS`, поэтому безопасна и на БД, где таблицы уже были).
- **`schema_migrations`** — таблица-журнал: какие версии уже применены.
- **[`app/migrate.py`](../app/migrate.py)** — раннер:
  1. подключается к Postgres (с ретраем — БД в контейнере может ещё стартовать);
  2. берёт `pg_advisory_lock` → мигрирует **ровно один** процесс, остальные ждут;
  3. создаёт `schema_migrations` (если нет);
  4. применяет каждую неприменённую миграцию **в своей транзакции** (DDL в Postgres
     транзакционен) и пишет версию в журнал;
  5. отпускает lock.

Идемпотентно: повторный запуск — `up to date`. Безопасно при параллельном старте многих
процессов (advisory-lock).

## Когда применяются

Автоматически, тремя путями — что сработает первым, то и накатит, остальные увидят
`up to date`:

- **Отдельный шаг compose** `migrate` — одноразовый сервис, применяет миграции и
  завершается; `api`/`worker`/`summarizer` ждут его через
  `depends_on: condition: service_completed_successfully` (а он сам ждёт
  `postgres: service_healthy`).
- **Старт api** — в lifespan вызывается `migrate()`.
- **Старт воркеров** — в начале `main()` каждого воркера.

Вручную:
```bash
docker compose run --rm migrate          # или:
python -m app.migrate
```

## Как добавить миграцию

1. Создать файл со следующим номером, напр. `migrations/0003_add_titles.sql`:
   ```sql
   -- 0003_add_titles: заголовки диалогов
   ALTER TABLE conversations ADD COLUMN IF NOT EXISTS title TEXT;
   ```
2. Всё. При следующем старте (или `python -m app.migrate`) она применится один раз.

**Правила:**
- Номер строго возрастает; файлы **не переименовывать и не менять** после применения на
  проде (иначе журнал разъедется). Исправления — новой миграцией.
- Держите миграции по возможности идемпотентными (`IF NOT EXISTS`, `ADD COLUMN IF NOT
  EXISTS`).
- **Большие таблицы:** обычный `CREATE INDEX` берёт блокировку на запись. Для больших
  боевых таблиц используйте `CREATE INDEX CONCURRENTLY` — но он **не может** идти в
  транзакции, поэтому такую миграцию выносите отдельным файлом и применяйте вне общего
  транзакционного пути (или отдельным ручным шагом). В текущем скелете таблицы малы —
  обычного индекса достаточно.

## Совместимость со старыми БД

`0001_init` идемпотентна, поэтому на БД, где схема уже создавалась прежним `schema.sql`,
она просто отметится применённой без изменений. Колонки/индексы, добавленные позже
(`message_id`, дедуп-индекс, индекс пагинации), приезжают своими миграциями.

Проверено: на чистой БД применяются `0001`+`0002`; повторный прогон — `up to date`;
`schema_migrations` содержит обе версии.
