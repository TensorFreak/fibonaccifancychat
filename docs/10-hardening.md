# 10. Харденинг: правки перед корпоративным тестом

Документ фиксирует изменения, внесённые по результатам ревью логики. Каждая правка —
проблема, решение, где в коде, как проверено. Верхнеуровнево код прошёл проверку:
импорты, `auth`, `tokens` (включая офлайн-фолбэк), гейт порядка, идемпотентность,
лента генерации, обработка ошибки LLM, бюджет промпта, replay, и весь SQL против
реального Postgres 16.

## C1. Авторизация и владение диалогом

**Было:** любой мог подключиться к `/ws/{любой_id}` и читать/писать чужой диалог;
`user_id` присылал клиент и он не проверялся.

**Стало:** [`app/auth.py`](../app/auth.py) + проверка владения в Postgres.

- Вебсокет требует токен: `ws://…/ws/{id}?token=…`. `authenticate(token)` → `user_id`
  (UUID) или отказ (`close 1008`). Dev-режим: токен детерминированно отображается в
  UUID пользователя; прод-режим (`auth_dev_mode=False`) — точка интеграции корп-SSO.
- `conversation_id` обязан быть валидным UUID (иначе отказ).
- [`db.ensure_conversation`](../app/db.py) идемпотентно создаёт `users`/`conversations`
  и возвращает, принадлежит ли диалог этому пользователю. Чужой → `close 1008`.

Побочный эффект: строки `conversations`/`users` теперь реально создаются (закрывает M4).
Примечание: api теперь делает одно обращение к Postgres (проверка владения) — это
сознательное исключение из принципа «api не трогает БД», т.к. владение проверяется
по источнику истины.

## C2. Резюме реально сохраняется в Postgres

**Было:** `save_summary` делал `UPDATE conversations … WHERE id=$1`, но строки диалога
никто не создавал → 0 строк обновлялось → резюме жило только в Redis-кэше и терялось
через 30 мин.

**Стало:** [`db.save_summary`](../app/db.py) — `INSERT … ON CONFLICT (id) DO UPDATE`
(upsert). Плюс диалог создаётся при подключении (C1). Проверено против реального
Postgres: `save_summary` → `get_summary` возвращает сохранённое, в т.ч. для диалога,
которого не было в `conversations`.

## C3. Идемпотентность (нет дублей И нет потерь при ретрае)

**Было (v1):** at-least-once + ретрай с начала `process` → повторная вставка сообщения юзера.

**Было (v2, промежуточно):** дедуп на Redis-маркерах `SET NX` — но маркер ставился ДО
вставки. Сбой в окне «маркер уже стоит, вставка ещё нет» → ретрай пропускал вставку →
**потеря сообщения** (at-most-once). Это подтвердилось прогоном.

**Стало (v3):** идемпотентность перенесена в Postgres — источник истины:

- В `messages` добавлены колонка `message_id` и **частичный уникальный индекс**
  `(message_id, role) WHERE message_id IS NOT NULL`.
- [`db.insert_message`](../app/db.py) делает `INSERT … ON CONFLICT DO NOTHING RETURNING id`
  и возвращает, была ли строка реально вставлена. Ретрай той же обработки не задваивает
  запись — гарантия на уровне БД, **без окна «маркер до действия»**.
- Ответ ассистента пишется с тем же `message_id` (роль различает строки), поэтому его
  вставка тоже exactly-once.
- Горячее окно ([`append_context`](../app/workers/llm_worker.py)) идемпотентно по `mid`
  (скан окна) и вызывается на каждой попытке — поэтому сбой между вставкой в БД и
  добавлением в окно **не теряет** сообщение из контекста.
- Эхо `user_message` и инкремент счётчика суммаризации привязаны к «реально добавили» —
  без дублей у клиента и без накрутки `since_sum`.
- Redis-маркеры дедупа (`msg_dedup`, `dedup_ttl_seconds`) удалены за ненадобностью.

Дополнительно: **перепроверка гейта порядка под замком** — пока воркер ждёт замок, тур мог
быть применён другим воркером (reclaim долгой генерации); повторная генерация не
запускается (нет лишнего вызова LLM).

Проверено прогоном на реальном Postgres: (0) `insert_message` возвращает `True/False` для
первой/повторной вставки; (1) ретрай после ошибки LLM — ровно 1 user + 1 assistant;
(2) сбой между вставкой и окном — сообщение НЕ потеряно и НЕ задвоено; (3) повтор
применённого `seq` — 0 повторных генераций.

## H1. FIFO-порядок при нескольких воркерах

**Было:** замок `lock:conv:{id}` предотвращал одновременность, но не переупорядочивание —
при `--scale worker=N` более позднее сообщение могло примениться раньше.

**Стало:** гейт порядка по монотонному `seq`.

- api присваивает `seq = INCR seq:conv:{id}` и кладёт его в задачу.
- Воркер ([`_order_gate`](../app/workers/llm_worker.py)) применяет только `seq == applied+1`.
  `seq ≤ applied` → пропуск (дубль/replay). `seq > applied+1` → предшественник ещё не
  применён: задача возвращается в хвост очереди (`XADD`) с короткой паузой. `applied`
  двигается строго после успеха, под замком.
- Deadlock-free: копия одна, крутится до своей очереди; предшественник обрабатывается
  другим воркером или reclaim-ом (см. L1).

Проверено: seq=2 при applied=0 возвращается в хвост и не применяется; seq=1 применяется;
`seq ≤ applied` пропускается.

## H2. Сериализация записи в WebSocket

**Было:** `pump_out` и несколько `tail_generation` писали в один сокет параллельно →
риск `concurrent send` в Starlette.

**Стало:** единый `asyncio.Lock` на соединение; вся отправка идёт через `send()` под
замком. [`api/main.py`](../app/api/main.py).

## H3. Лента генерации всегда завершается

**Было:** ошибка LLM посреди генерации оставляла ленту без `end` и без TTL → утечка в
Redis навсегда, клиент без `assistant_end`.

**Стало:** генерация обёрнута в `try/except`; при ошибке в ленту пишется
`{"t":"end","error":"1"}`, ставится `expire`, снимается `active_gen`, затем исключение
пробрасывается (→ не ackается, уйдёт в ретрай). [`llm_worker.process`](../app/workers/llm_worker.py).

Проверено: при падении LLM лента получает терминальную запись с `error=1`, TTL > 0,
`active_gen` снят, `applied` НЕ продвинут, исключение проброшено. `tail_generation`
транслирует `assistant_end` с полем `error`.

## H4. tiktoken в закрытом контуре

**Было:** первый вызов tiktoken мог ходить в интернет за BPE-рангами → падение офлайн.

**Стало:** [`app/tokens.py`](../app/tokens.py) — если энкодер получить не удалось,
включается грубая эвристика (~3 символа/токен, с запасом в бо́льшую сторону), сервис не
падает. Кэш рангов для точного подсчёта теперь **вшит в образ** ([`Dockerfile`](../Dockerfile)
прекачивает `o200k_base`+`cl100k_base`, `TIKTOKEN_CACHE_DIR` задан) — офлайн-эвристика
остаётся страховкой, а не штатным путём (см. также R6-2 про неблокирующий вызов).

Проверено: при недоступном энкодере `count_text`/`truncate_text`/`chunk_messages`
работают на эвристике.

## M1. Watermark суммаризации по `id`, а не `created_at`

**Было:** `created_at > since` — при одинаковых таймстампах сообщения на границе могли
потеряться из summary.

**Стало:** колонка `conversations.summary_upto_id BIGINT`, выборка `id > $2 ORDER BY id`,
watermark = `id` последнего свёрнутого. Монотонный `id` не даёт коллизий.
[`migrations/`](../migrations), [`db.py`](../app/db.py), [`summarizer.py`](../app/workers/summarizer.py).
`load_recent_messages` тоже переведён на `ORDER BY id DESC`.

Проверено против Postgres: сдвиг watermark выдаёт дальше только новые сообщения.

## M2. Валидация и лимиты входа

**Стало:** входной цикл [`api/main.py`](../app/api/main.py) не роняет соединение на
кривом JSON/пустом/слишком длинном тексте — отвечает событием `{"type":"error",…}` и
продолжает. Потолок длины — `max_message_chars` (8000).

## M5. Уникальные имена консьюмеров

**Было:** все реплики звались `worker-1`/`summarizer-1` → для Redis это один консьюмер,
PEL/`XAUTOCLAIM` работали некорректно.

**Стало:** `CONSUMER_NAME = "{hostname}-{pid}-{rnd}"` в обоих воркерах.

## L1. Реклейм зависших задач (XAUTOCLAIM)

**Стало:** [`llm_worker.reclaim_stale`](../app/workers/llm_worker.py) периодически (раз в
`reclaim_every_iters` итераций) забирает у «мёртвых» воркеров задачи, висящие в PEL
дольше `reclaim_min_idle_ms`, и дообрабатывает. Это же не даёт «залипнуть» гейту
порядка, если предшественник застрял в PEL умершего воркера. Разбор ответа устойчив к
версии Redis (2 или 3 элемента в ответе XAUTOCLAIM).

## L3. Мягкая остановка

**Стало:** оба воркера ловят `SIGINT`/`SIGTERM`, дообрабатывают текущее сообщение и
выходят из цикла — корректный rolling-деплой без обрыва активной обработки.

## P. Прод-готовность инфраструктуры (проход по CRITICAL-ревью)

Отдельный проход по замечаниям прод-ревью (см. корневой `review.md`). Внесено:

- **Границы стримов (Redis OOM).** `XADD … MAXLEN ~` на `chat:inbound` и `chat:summarize`
  (`inbound_stream_maxlen`, `summarize_stream_maxlen`). Без этого стрим рос бы без границ:
  `XACK` убирает из PEL, но не из стрима. Проверено: 5000 XADD с `MAXLEN ~ 100` → `XLEN=100`.
- **Таймауты LLM.** [`llm/client.py`](../app/llm/client.py): connect/read/write из конфига +
  переиспользуемый `AsyncClient`. Раньше `Timeout(None)` — зависшее соединение блокировало
  воркер навсегда.
- **TTL замка + heartbeat.** `conv_lock_ttl_seconds` (300) вместо хардкода 120; фоновый
  `_heartbeat_lock` продлевает замок во время генерации. Иначе длинный ответ пережил бы
  TTL → дублирующая обработка. Проверено: генерация 4 c при TTL 2 c — замок жив, генерация одна.
- **Liveness FIFO-гейта.** Если предшественник (`seq-1`) не приходит дольше
  `order_gap_timeout_ms`, разрыв перешагивается (иначе сообщение кружило бы по очереди
  вечно при потерянном `seq`). Проверено: applied перескакивает через дыру.
- **Батчинг + реклейм суммаризатора.** `load_messages_since` с лимитом `summary_max_fetch`
  (защита от OOM при отставании) и дозапуском при обрезке; в суммаризатор добавлен
  `reclaim_stale` (PEL). Проверено: watermark сдвигается, дозадача ставится в очередь.
- **bcrypt в threadpool.** `hash_password`/`verify_password` теперь `async` через
  `asyncio.to_thread` — не блокируют event loop api; пароль обрезается до 72 байт (не
  крашится) и ограничен `password_max_chars`.
- **Resume events tail.** `pump_out` переживает рестарт/обрыв Redis: повторяет `XREAD` ленты
  `events:{id}` с того же `last_id` (события durable — ничего не теряется) и делает повторный
  догон `active_gen` (ловит генерацию, начавшуюся до курсора клиента). *(Ранее control-канал
  был Pub/Sub с переподпиской — переведён на durable Stream `events:{id}`, см. [02](02-websocket-api.md), [07](07-resumable-streams.md).)*
- **Фейл-фаст секрета.** Валидатор конфига не даёт подняться с дефолтным `auth_secret` при
  `auth_dev_mode=false`. Проверено.
- **Non-root контейнер.** Dockerfile создаёт `appuser`; api за прокси — `--proxy-headers`.

## R2. Прод-ревью, проход 2 (2026-08-12): критичные и high-фиксы

Второй прод-проход по всей кодовой базе. Закрыты дефекты, не пойманные первым проходом:
fail-open дефолт auth, некорректное снятие распределённого замка и три риска
ресурсов/потери данных под нагрузкой и при падении. (Метки `R2-*` — чтобы не путать с
`C*/H*` выше, которые нумеруют другой проход.)

### R2-1 (CRITICAL). Fail-open дефолт авторизации

**Было:** `auth_dev_mode` по умолчанию `True`. В dev-режиме `authenticate()` принимает
ЛЮБУЮ строку-токен как личность (`uuid5`) — то есть auth фактически выключен. Деплой «на
дефолтах» или забытая переменная → полный обход авторизации. Старт-гард проверял секрет
ТОЛЬКО при `auth_dev_mode=False`, т.е. именно на опасном пути гарда не было.

**Стало:** [`config.py`](../app/config.py) — `auth_dev_mode` по умолчанию **`False`**
(fail-closed); dev-режим включается только явно. Плюс усилен `_guard_auth_secret`: в
не-dev режиме старт отклоняется не только на дефолтном секрете, но и на известных
плейсхолдерах из `.env.example` и на секретах короче 32 символов — иначе оператор,
скопировавший пример и забывший сгенерировать ключ, поднялся бы с публично известным
секретом. Проверка: `Settings()` бросает `ValueError` при `AUTH_DEV_MODE=false` + слабый
`AUTH_SECRET`; проходит при заданном длинном секрете.

### R2-2 (CRITICAL). Небезопасное снятие распределённого замка

**Было:** [`llm_worker.process`](../app/workers/llm_worker.py) снимал замок диалога
безусловным `DEL` в `finally`. Если TTL истёк на лету (пауза event loop, heartbeat не
успел продлить), замок мог перехватить другой воркер — и наш `DEL` снёс бы ЧУЖОЙ замок →
параллельная обработка одного диалога (ровно то, что замок исключает). Heartbeat проверял
владение перед продлением, а снятие — нет.

**Стало:** новый модуль [`app/locks.py`](../app/locks.py) — `release_lock()` снимает замок
атомарно и только если значение всё ещё наше (Lua `GET==token → DEL`, без гонки между
проверкой и удалением). Задействован в `llm_worker` и в `summarizer` (там же значение
замка переведено с константы `"1"` на уникальный `CONSUMER_NAME`, иначе сравнение
бессмысленно). Проверка: код-ревью Lua (owner-aware), оба воркера снимают только свой замок.

### R2-3 (HIGH). Утечка ленты токенов при жёстком падении воркера

**Было:** лента `gen:{id}:{mid}` создавалась `XADD` БЕЗ TTL; финальный `gen_ttl` ставился
только после записи `end`. Жёсткое падение (SIGKILL/OOM) до `end` → лента (тысячи записей)
оставалась в Redis без TTL НАВСЕГДА. `active_gen` протухал, ленту никто не чистил →
монотонная утечка памяти Redis от упавших генераций.

**Стало:** [`llm_worker.process`](../app/workers/llm_worker.py) ставит active-TTL
(`gen_active_ttl_seconds`, 900 c) на первом токене и продлевает раз в 256 токенов (дёшево).
Брошенная лента протухает через `gen_active_ttl` после последнего токена; после `end` —
финальный `gen_ttl` как раньше. Риск протухания под живым медленным стримом закрыт тем,
что active-TTL держат заметно больше паузы между токенами (`llm_read_timeout`).

### R2-4 (HIGH). Флуд в общий inbound-стрим → тихая потеря сообщений ДРУГИХ юзеров

**Было:** все диалоги идут в один `chat:inbound` с приблизительным `MAXLEN`. Рейтлимита
не было (только лимит длины). Один клиент мог заливать стрим быстрее, чем воркеры
разгребают; при переполнении `MAXLEN` вырезает СТАРЫЕ записи — включая ещё НЕ доставленные
(`>`) сообщения чужих диалогов. Потеря молчаливая (ни ошибки, ни записи в PEL).

**Стало:** per-user рейтлимит на входе вебсокета
([`_allow_ws_message`](../app/api/main.py)) — фиксированное окно `INCR`+`EXPIRE`
(`ws_rate_max_messages`/`ws_rate_window_seconds`, дефолт 30/10 c), атомарно и общее между
инстансами api. Проверка идёт ДО расхода `seq` и `XADD` — отклонённое сообщение не создаёт
дыру в порядке и не попадает в стрим; клиенту уходит `{"type":"error","error":"rate_limited"}`.
Примечание: это первый рубеж; сетевой L7-лимит на прокси и шардирование стрима остаются
рекомендацией для масштаба.

### R2-5 (HIGH). Пропуск разрыва FIFO-гейта мог тихо терять реальные сообщения

**Было:** liveness-таймаут гейта (`order_gap_timeout_ms`, был 30 c) не различает «сообщение
потеряно» и «ещё не вычитано из-за backlog». Под завалом предшественник может просто ждать
вычитки; при таймауте меньше худшей задержки очереди гейт перешагивал разрыв, а опоздавшее
РЕАЛЬНОЕ сообщение потом отсеивалось как `seq<=applied` → тихая потеря хода, причём именно
под нагрузкой.

**Стало:** дефолт поднят до **120 c** (консервативно; держать > p99 задержки
«XADD → вычитка» на пике). Каждый пропуск логируется громко как событие потери:
`[order][LOSS] conv=… dropping seq A..B` ([`_order_gate`](../app/workers/llm_worker.py)) —
заведите на него алерт; частые срабатывания = поднять таймаут или разгрузить очередь.
Природа тайм-аута документирована как зависящая от нагрузки, а не только от отказов.

## R3. Прод-ревью, проход 3 (2026-08-12): MEDIUM-фиксы

Третий проход по MEDIUM-замечаниям. Все правки сделаны КОГЕРЕНТНО с существующей
логикой (порядок FIFO, идемпотентность, тайминги замка/реклейма).

### R3-M1 (MEDIUM). Безлимитный рост счётчиков диалога в Redis

**Было:** `seq:conv:*`, `applied:conv:*`, `since_sum:*` писались через `INCR/SET/INCRBY`
БЕЗ TTL. В отличие от `ctx:`/`sum:`/`title:enq` (все с TTL), эти жили вечно — по триплету
на КАЖДЫЙ диалог за всю жизнь сервиса → медленный рост памяти Redis без эвикции.

**Стало:** всем трём задан idle-TTL `conv_counter_ttl_seconds` (1 сутки), обновляемый на
активности. **Тонкость коэрентности:** `seq` и `applied` держат инвариант порядка, и
наивный TTL сломал бы FIFO — если `applied` переживёт `seq`, то после сброса `seq` первое
же новое сообщение получило бы `seq<=applied` и было бы ТИХО ОТБРОШЕНО. Решение
([`_mark_applied`](../app/workers/llm_worker.py)): воркер продлевает `seq` и `applied`
одним TTL в один момент, а api при `INCR` может лишь продлить `seq` ДАЛЬШЕ. Значит
`ttl(seq) >= ttl(applied)` всегда → «остывший» диалог протухает целиком и начинает счёт с
нуля (безопасно: это чисто redis-токены порядка, не связанные с id в Postgres).
Единственное допустимое асимметричное состояние — `seq` жив, `applied` истёк — даёт
самоизлечивающийся `WAIT` (через gap-timeout), но НИКОГДА не дроп.

Проверка (симуляция на Redis): инвариант `ttl(seq) >= ttl(applied)` держится на каждом
шаге; воспроизведён баг наивного TTL (`applied` высок + `seq` сброшен → `DROP`) как
доказательство опасности; наша дисциплина даёт после простоя чистый рестарт (`APPLY`), а
в асимметрии — `WAIT`, не `DROP`.

### R3-M2 (MEDIUM). At-least-once генерация: двойной вызов LLM + расхождение клиент/БД

**Было:** падение воркера МЕЖДУ вставкой ответа ассистента ([`llm_worker`](../app/workers/llm_worker.py))
и отметкой `applied` заставляло reclaim переиграть весь ход: второй ПЛАТНЫЙ вызов LLM,
чей ответ клиент видел вживую, — но строка ассистента дедуплится (`ON CONFLICT
(message_id,'assistant') DO NOTHING`), так что в БД оставался ПРЕЖНИЙ ответ, а юзер видел
НОВЫЙ. На перезагрузке — расхождение. Плюс преждевременный reclaim заставлял второй воркер
крутиться на замке всю генерацию.

**Стало:**
- Идемпотентность ВСЕГО хода: перед генерацией воркер проверяет
  [`db.assistant_exists`](../app/db.py) — если ответ на этот `message_id` уже в Postgres,
  генерация НЕ повторяется, просто досдвигается `applied`. Ответ уже сохранён и (при первой
  попытке) отстримлен. Опирается на тот же частичный уникальный индекс `(message_id, role)`.
- Тайминги замка/реклейма зафиксированы валидатором конфига
  ([`_check_lock_and_reclaim_timing`](../app/config.py)): `lock_heartbeat_seconds <
  conv_lock_ttl_seconds` (heartbeat продлевает замок до истечения) и `reclaim_min_idle_ms >=
  conv_lock_ttl_seconds*1000` (не забирать задачу раньше, чем истёк бы замок мёртвого
  воркера — иначе живого-но-долгого воркера реклеймят на лету). Дефолт `reclaim_min_idle_ms`
  поднят 120000 → 300000 (= TTL замка).

Проверка: валидатор отвергает `reclaim < lock_ttl*1000` и `heartbeat >= lock_ttl`, дефолты
проходят; `assistant_exists` — короткий `SELECT 1` по дедуп-индексу.

### R3-M3 (MEDIUM). Нет таймаута запросов Postgres → исчерпание пула

**Было:** [`db.get_pool`](../app/db.py) — `max_size=10`, но без `command_timeout` и без
серверного `statement_timeout`. Один зависший/медленный запрос держит соединение
бесконечно; горстка таких исчерпывает пул и останавливает процесс.

**Стало:** пул создаётся с `command_timeout` (клиентская отмена, `pg_command_timeout`=30 c)
и `server_settings={"statement_timeout": …}` (серверный предел, `pg_statement_timeout_ms`=
30000). Раннер миграций идёт по ОТДЕЛЬНОМУ соединению (`migrate.py`) и под лимит не
попадает — длинный DDL не оборвётся.

## R4. Прод-ревью, проход 4 (2026-08-12): HIGH + MEDIUM по корректности

Свежий сквозной проход по КОДУ (не по докам). Логика бэкенда сохранена; правки точечные.

### R4-H1 (HIGH). Стриминг молча умирал при TTFT > 5 c

**Было:** воркер ставит `active_gen`, кладёт `gen_start` в ленту `events:{id}`, и только ПОТОМ идёт к модели —
первый токен ленты `gen:{id}:{mid}` появляется лишь когда модель ответит. До этого ленты
НЕ существует. Клиентский тейл ([`tail_generation`](../app/api/main.py)) на пустом `xread`
(block=5000) проверял `exists(gen_key)` и, не найдя ленты, СДАВАЛСЯ. Если time-to-first-token
дольше 5 c (норма для большого контекста/медленной модели), тейл выходил навсегда: клиент
оставался с пустым «пишет…» баблом, хотя ответ шёл. Не потеря данных (ответ в ленте и в
Postgres, виден при перезагрузке истории), но тихая поломка resumable-стриминга ровно в
целевом сценарии проекта.

**Стало:** различаем «ленты ЕЩЁ нет» и «лента УЖЕ протухла». Сдаёмся только если генерация
больше не активна — `active_gen` (ставится ДО `gen_start`, снимается по завершении) уже НЕ
указывает на этот `message_id`. Пока указывает (TTFT) — ждём дальше. Нормальное завершение
по-прежнему выходит по записи `end` раньше этой ветки. При падении/вытеснении `active_gen`
перестаёт указывать на нас (истекает по TTL или перезаписывается новой генерацией) → тейл
корректно выходит.

Проверка (симуляция на Redis): TTFT (лента отсутствует, `active_gen==mid`) → ждём; первый
токен (лента есть) → работаем; завершение+протухание (`active_gen` снят) → выход;
вытеснение новой генерацией (`active_gen==другой mid`) → выход.

### R4-M1 (MEDIUM). Замок суммаризатора истекал под долгой свёрткой

**Было:** замок `lock:sum:{id}` брался с хардкодом `ex=120` и БЕЗ heartbeat. Свёртка
большого хвоста (`summary_max_fetch` до 5000 сообщений, чанки по 8000 токенов = много
LLM-вызовов) могла превысить 120 c; замок истекал на лету, и второй суммаризатор дублировал
работу. Не потеря данных (`save_summary` идемпотентен по диапазону `id>watermark`,
last-writer-wins на эквивалентном результате), но лишний расход LLM.

**Стало:** TTL замка вынесен в конфиг (`summarize_lock_ttl_seconds`, 300 c) и продлевается
heartbeat'ом — тем же owner-aware примитивом, что и в llm_worker. Общая логика замков
вынесена в [`app/locks.py`](../app/locks.py): `heartbeat_lock` (продлевает ТОЛЬКО свой
замок) + `release_lock` (снимает ТОЛЬКО свой). `llm_worker` переведён на этот же общий
`heartbeat_lock` (поведение идентично прежнему локальному). Валидатор конфига требует
`lock_heartbeat_seconds < summarize_lock_ttl_seconds`.

Проверка: валидатор отвергает `heartbeat >= summarize_lock_ttl`, дефолты проходят; общий
`heartbeat_lock` компилируется и вызывается из обоих воркеров.

## R5. Прод-ревью, проход 5 (2026-08-12): LOW-фиксы + читаемые логи

### R5-1 (LOW). Моргание Redis больше не роняет вебсокет

## R6. Прод-ревью, проход 6 (2026-08-12): пропускная способность воркера + неблокирующий tiktoken

Сквозной проход по коду (не по докам) под масштаб «gpt-like». Два HIGH: воркер не
использовал asyncio по назначению, и синхронный tiktoken мог блокировать event loop.
Логика (FIFO-порядок, идемпотентность, resumable) сохранена — правки касаются только
того, КАК цикл раздаёт работу и КАК считаются токены.

### R6-1 (HIGH). Воркер вёл ровно одну генерацию за раз

**Было:** главный цикл ([`llm_worker.main`](../app/workers/llm_worker.py)) читал `count=1`
и полностью `await`-ил `process()` — включая весь стрим ответа LLM под замком диалога —
прежде чем прочитать следующее сообщение. Итог: суммарное число ОДНОВРЕМЕННЫХ генераций
по всему флоту = числу процессов-воркеров. Генерация же почти всё время просто ждёт сеть
LLM (event loop простаивает), поэтому это ровно антипаттерн, который asyncio призван
устранять. Масштабировать приходилось процессами, а это упирается в пул Postgres (каждый
процесс — свой пул до 10 соединений; ~10 воркеров исчерпывают дефолтный `max_connections=100`).

**Стало:** цикл раздаёт сообщения фоновым задачам (`_process_and_ack` через `_dispatch`),
удерживая не больше `worker_concurrency` (дефолт 24) одновременно:
- читаем из группы ровно `worker_concurrency − len(inflight)` сообщений (`count=available`),
  чтобы не захватывать в свой PEL больше, чем ведём (иначе задачи копились бы, а
  простаивающие воркеры не могли бы их взять);
- при заполнении ждём `asyncio.wait(..., FIRST_COMPLETED)` — без busy-wait;
- `reclaim_stale` теперь тоже РАЗДАЁТ реклеймленные задачи фоновым задачам, а не блокирует
  цикл на всю генерацию; dead-letter (без LLM) остаётся на месте;
- мягкая остановка ждёт активные генерации (`asyncio.gather(*inflight)`) — ответы не рвутся.

**Порядок и корректность НЕ ослаблены:** параллелятся только РАЗНЫЕ диалоги. Внутри
диалога seq-гейт возвращает не-свой-черёд в хвост, а замок `lock:conv:{id}` сериализует —
как и раньше (H1, R2-2). Провёл трассировку конкурентного случая: сообщения `seq=N` и
`N+1`, выданные одновременно, — `N+1` упирается в гейт и ждёт, пока `applied` дойдёт до `N`.

**Валидатор:** `worker_concurrency >= 1` ([`config.py`](../app/config.py)).
Масштабирование: сначала поднимать `worker_concurrency` (не множит пулы PG), потом реплики
(см. [12. Масштабирование](12-scaling.md), §2).

Проверено юнит-тестами (см. ниже): учёт `inflight` (слот занят на время задачи, освобождён
по завершении), `XACK` при успехе и ОТСУТСТВИЕ ack при ошибке; инварианты `_order_gate`.

### R6-2 (HIGH). Синхронный tiktoken в event loop воркера

**Было:** [`tokens._encoding`](../app/tokens.py) при первом вызове мог ходить в сеть за
BPE-рангами, а `enc.encode()` — CPU-затратный и синхронный. Всё это вызывалось напрямую из
async-кода в `build_prompt` (и в `summarizer.fold`). Медленный/зависший поход tiktoken или
просто большой промпт БЛОКИРОВАЛИ бы весь event loop воркера — включая `heartbeat_lock`.
Если heartbeat не успевает продлить замок до `conv_lock_ttl`, замок истекает на лету, и
второй воркер берётся за диалог (лишний вызов LLM ловит перепроверка `applied`, но
пропускная способность и инварианты замка страдают).

**Стало:**
- CPU-часть сборки промпта вынесена в чистую функцию `_assemble_prompt` и вызывается через
  `asyncio.to_thread` ([`build_prompt`](../app/workers/llm_worker.py)); в суммаризаторе так
  же обёрнуты `chunk_messages`/`truncate_text` ([`fold`](../app/workers/summarizer.py)).
  tiktoken (Rust) отпускает GIL → в потоке реально параллелится по ядрам.
- Новая [`tokens.warm_encoder`](../app/tokens.py) прогревает энкодер на старте ОБОИХ
  воркеров (через `to_thread`) — возможный сетевой поход случается один раз при загрузке,
  не в первой генерации.
- Кэш BPE-рангов **вшит в образ**: [`Dockerfile`](../Dockerfile) прекачивает `o200k_base`
  и `cl100k_base` в `TIKTOKEN_CACHE_DIR` на этапе сборки — в проде сетевого похода нет вовсе.

### R6-3. Закоммиченный набор юнит-тестов

**Было:** проверки шли ад-хок, в репозитории тестов не было (MEDIUM-замечание прошлых ревью).

**Стало:** [`tests/`](../tests) на `pytest` + `pytest-asyncio` (dev-зависимости в
[`requirements-dev.txt`](../requirements-dev.txt)), без внешних сервисов (in-memory
fake-Redis):
- `test_order_gate.py` — инварианты FIFO-гейта (legacy passthrough, дубль-скип, in-order,
  re-queue разрыва, gap-timeout skip) — то, что удерживает порядок при параллельных
  генерациях (R6-1);
- `test_dispatch.py` — учёт `inflight` и ack/no-ack (R6-1);
- `test_assemble_prompt.py` — отбор по токен-бюджету, summary-как-system, аварийная обрезка,
  непопадание служебного `mid` в LLM.

Запуск (хост-Python может быть < 3.10; образ прод-рантайма — 3.12):
`docker run --rm -v "$PWD":/srv -w /srv python:3.12-slim bash -c "pip install -q -r requirements-dev.txt && python -m pytest"`.
Прогон: **10 passed**.

## R7. Прод-ревью, проход 7 (2026-08-12): critical/high по инфраструктуре и учёту

### R7-1 (CRITICAL). Postgres был открыт наружу под учёткой `app/app`

**Было:** `docker-compose.yml` публиковал `ports: ["5432:5432"]`. На сервере с публичным IP
БД (источник истины: юзеры, хеши паролей, вся история) была доступна снаружи с тривиальными
кредами из `.env`.

**Стало:** маппинг порта убран — доступ к Postgres только из внутренней сети compose (как у
Redis). Креды параметризованы (`POSTGRES_USER`/`POSTGRES_PASSWORD`/`POSTGRES_DB`, дефолт
`app/app` только для локали; в проде — сильный пароль + синхронный `POSTGRES_DSN`). Для
локальной отладки порт можно вернуть, привязав ТОЛЬКО к `127.0.0.1` (комментарий в compose).

### R7-2 (HIGH). Учёт ws-соединений врал для долгоживущих сокетов

**Было:** потолок соединений считался счётчиком `INCR`/`DECR` с safety-TTL
`conv_lock_ttl*2` (=600 c). WebSocket живёт часами: ключ протухал под открытым сокетом, а
последующий `DECR` уводил счётчик в минус — и лимит переставал срабатывать (или обходился
терпеливым клиентом).

**Стало:** учёт — ZSET дедлайнов (`member` = id соединения, `score` = время протухания). На
входе выкидываем протухшие записи (`ZREMRANGEBYSCORE`), добавляем себя, считаем `ZCARD`;
живое соединение продлевает свой `score` heartbeat'ом раз в `lock_heartbeat_seconds`; запись
мёртвого инстанса выпадает сама. Не уходит в минус и не теряет учёт долгих сокетов. Новый
параметр `ws_conn_ttl_seconds` (90 c), валидатор требует `> lock_heartbeat_seconds`.

### R7-3 (HIGH). Молчаливая «дыра» в контексте при отставании суммаризатора

**Было:** если суммаризатор долго не успевал/падал (в т.ч. dead-letter), watermark стоял, а
горячее окно уезжало вперёд — сообщения между watermark и началом окна выпадали из промпта
незаметно (они в Postgres, но не в summary и не в окне).

**Стало:** когда суммаризатор ВИДИТ несвёрнутый хвост длиннее горячего окна
(`len(pending) > ctx_max_messages` — признак дыры), он логирует `[summary][LAG]` И пишет
событие в durable-поток `chat:summarize:lag` (как `order_loss` в C3) — заведите на него
алерт. Сама свёртка ниже лечит отставание (двигает watermark); аудит убирает молчаливость.

## Что осталось за рамками (осознанно)

- **Реальный корп-SSO** не реализован — только шов `app/auth.py` (`auth_dev_mode=False`
  бросает `NotImplementedError`). Перед прод-контуром обязательно подключить.
- **Реконнект за пределами TTL лент** (`gen_ttl_seconds` / `events_ttl_seconds`) — токены и
  эхо `user_message` уже недоступны для догона; клиент восстанавливает состояние
  перезагрузкой истории из Postgres. В пределах TTL и то, и другое resumable (durable-ленты
  `gen:{}` / `events:{}`, догон по `last_event_id`).
- **Секреты/TLS**: порты БД/Redis наружу больше НЕ публикуются (R7-1), но Redis по-прежнему
  без пароля, а дефолтный `POSTGRES_PASSWORD=app` — для локали; в корп-контуре задать сильные
  пароли и TLS на уровне инфраструктуры.
- **Шардирование inbound-стрима** не введено; гейт порядка решает корректность, но
  единый стрим остаётся точкой нагрузки на масштабе.
