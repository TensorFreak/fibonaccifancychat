# 12. Масштабирование: что менять

Приложение спроектировано под горизонтальное масштабирование — всё межпроцессное
состояние в Redis/Postgres, у процессов нет локального состояния, нужного соседям.
Мультиинстансовость проверена: два инстанса FastAPI за «балансировкой» корректно
обмениваются событиями через Redis в обе стороны. Ниже — что именно нужно донастроить
на каждом уровне при росте нагрузки.

## Сводка: сколько чего запускать

| Компонент | Как масштабируется | Ограничитель |
|---|---|---|
| `api` (FastAPI) | N инстансов за балансировщиком | число вебсокет-соединений |
| `worker` | `worker_concurrency` в процессе, затем `--scale worker=N` | число ОДНОВРЕМЕННЫХ генераций (1 воркер = `worker_concurrency` генераций) |
| `summarizer` | `--scale summarizer=N` (своя группа) | обычно 1–2 хватает, работа фоновая |
| `redis` | 1 инстанс (общее состояние) | точка нагрузки; при экстремуме — Redis Cluster |
| `postgres` | 1 инстанс (+ реплики на чтение при нужде) | число соединений, диск |

Реальный потолок часто **не сервер, а лимиты LLM API** (запросов/токенов в минуту) —
проверьте квоты модели под ожидаемую нагрузку.

## 1. api — нужен балансировщик

Приложение к нескольким инстансам готово (sticky-сессии НЕ нужны: реконнект на любой
инстанс восстанавливается из `active_gen` + реплея ленты). Что поменять в инфраструктуре:

1. **Хост-порт у `api` уже снят** (H3): в [`docker-compose.yml`](../docker-compose.yml)
   стоит `expose: ["8000"]` (не `ports`), поэтому `--scale api=N` не конфликтует по порту.
2. **reverse-proxy/LB уже включён** — сервис `caddy` (см. [`Caddyfile`](../Caddyfile)) —
   и он же:
   - раскидывает HTTP/WS-запросы по репликам api (по DNS-имени `api`);
   - **пропускает WebSocket-upgrade** из коробки;
   - терминирует TLS (автоматический сертификат при `SITE_ADDRESS=домен`).
3. Поднять реплики: `docker compose up -d --scale api=3`.

Балансировщик на Caddy (`Caddyfile`, WebSocket проксируется из коробки):
```
{$SITE_ADDRESS} {
    reverse_proxy api:8000    # Caddy сам разложит по репликам сервиса api
}
```

Sticky-сессии включать НЕ требуется, но и не вредят. TLS — на этом же прокси
(см. [11. Веб и деплой](11-web-and-deploy.md)).

## 2. worker — сначала `worker_concurrency`, потом реплики

**Один воркер ведёт `worker_concurrency` генераций РАЗНЫХ диалогов одновременно**
(дефолт 24, [10](10-hardening.md), R6-1). Генерация почти всё время ждёт сеть LLM,
поэтому один asyncio-процесс дёшево мультиплексирует десятки таких ожиданий на одном
ядре — плодить процессы ради параллелизма НЕ нужно. Число одновременных ответов ≈
`worker_concurrency × число реплик`.

**Порядок роста — важен:**
1. **Сначала поднимайте `worker_concurrency`** (env). Это НЕ множит соединения Postgres:
   у процесса один пул asyncpg (`pg_pool_max_size`, дефолт 32), а короткие запросы (вставка,
   регидратация) берут и быстро отпускают соединение, т.к. во время самого стрима LLM
   соединение к БД не удерживается. ИНВАРИАНТ (H1): `worker_concurrency <= pg_pool_max_size`
   (валидатор в `config.py`) — пул должен покрывать пик одновременных запросов.
2. **Потом добавляйте реплики** `--scale worker=N` — но помните: КАЖДЫЙ процесс поднимает
   свой пул до `pg_pool_max_size` соединений. Суммарно к БД = `pg_pool_max_size × (api +
   worker + summarizer)`; держите ниже `max_connections=100` Postgres. То есть масштабирование
   ПРОЦЕССАМИ упирается в Postgres раньше, чем в ядра, — отсюда правило «сначала concurrency»
   (и согласуйте `pg_pool_max_size` с числом реплик).

```bash
# вертикально: больше параллельных генераций на процесс (env)
WORKER_CONCURRENCY=48
# горизонтально: больше процессов (когда одного мало по CPU/сети)
docker compose up -d --scale worker=4
```

Правило: держите `worker_concurrency` заметно ниже пула Postgres и лимитов Redis;
суммарная ёмкость `worker_concurrency × реплики` ≈ пик одновременных ответов.
Уже готово к масштабированию без доработок:
- уникальные имена консьюмеров (`hostname-pid-rnd`) — PEL/`XAUTOCLAIM` работают корректно;
- FIFO-порядок в диалоге держит гейт по `seq` (а не только замок), см. [10](10-hardening.md), H1;
  параллелятся только РАЗНЫЕ диалоги, порядок ВНУТРИ диалога сохранён (R6-1);
- реклейм зависших задач (`reclaim_stale`) забирает работу у умерших воркеров.

## 3. Postgres — следите за числом соединений

Каждый процесс (`api`, `worker`, `summarizer`) поднимает пул asyncpg до `pg_pool_max_size`
(дефолт 32, [`db.py`](../app/db.py)). При масштабировании суммарно:

```
соединений ≈ (кол-во api + кол-во worker + кол-во summarizer) × pg_pool_max_size
```

Postgres по умолчанию `max_connections = 100`. При `pg_pool_max_size=32` уже 3–4 процесса
упрутся в лимит — согласуйте `pg_pool_max_size`, `worker_concurrency` и число реплик. Что
делать при росте:
- уменьшить `pg_pool_max_size` (env) — но не ниже `worker_concurrency` (валидатор H1);
- либо поставить **PgBouncer** (transaction pooling) перед Postgres — стандартное решение;
- поднять `max_connections` в Postgres (осторожно, каждое соединение = память).

Для чтения (история, список диалогов) при большой нагрузке можно добавить **реплику на
чтение**, но для «десятков пользователей» это избыточно.

## 4. Redis — общее состояние, точка внимания

Redis — единая точка, через которую идёт вся координация (очереди, ленты токенов и
событий, кэш, замки, seq; Pub/Sub не используется). Для десятков-сотен пользователей
одного инстанса Redis достаточно.
Точки роста при большом масштабе:

- **Единый inbound-стрим** `chat:inbound` — единая точка нагрузки. Шардирование:
  `chat:inbound:{hash(conversation_id) % K}` с K группами воркеров. FIFO-порядок при этом
  уже обеспечен гейтом по `seq`, но шардинг снимает горячую точку. Не реализовано —
  осознанное упрощение скелета.
- **Память под ленты генераций** `gen:{id}:{mid}` — эфемерны, живут `gen_ttl_seconds`
  (300 c) после завершения. При очень высокой частоте генераций держите TTL умеренным.
- **Память под ленты событий** `events:{id}` — живут `events_ttl_seconds` (900 c),
  ограничены `events_maxlen`. События крошечные и редкие на фоне токенов — обычно не узкое
  место, но при большом числе активных диалогов учитывайте в общем бюджете памяти Redis.
- **Redis Cluster / Sentinel** — только на экстремальных объёмах или ради HA; для теста и
  умеренного прода не нужно.
- **Персистентность Redis (C2)** — compose запускает `redis:7` с `--appendonly yes`
  (`appendfsync everysec`) и томом `redisdata:/data`. Это ВАЖНО, а не опция: Redis здесь —
  durable-очередь принятых сообщений (`chat:inbound`) и источник истины порядка
  (`seq`/`applied`). Без AOF+тома рестарт/пересоздание контейнера потерял бы принятые, но
  ещё не сохранённые в Postgres сообщения. Горячий кэш (`ctx:`/`sum:`) при потере просто
  регидратируется из Postgres.

## 5. Ресурсы сервера (ориентир)

Основную нагрузку (генерацию токенов) несёт внешний LLM, сервер — лёгкий диспетчер.

| Профиль | vCPU | RAM | Кому |
|---|---|---|---|
| Минимум | 2 | 2 ГБ | впритык |
| Комфортно | 2 | 4 ГБ | десятки пользователей, 3–5 воркеров |
| С запасом | 4 | 8 ГБ | большой 256k-контекст / рост |

Всё (postgres, redis, api, worker, summarizer) помещается на одном сервере. Диск — SSD
20–40 ГБ (история сообщений — текст, растёт медленно). Добавьте swap 1–2 ГБ и
`restart: unless-stopped` в compose.

## 6. Эксплуатационное

- **`restart: unless-stopped`** на все сервисы — переживать перезагрузку сервера.
- **Healthcheck** на `api` (`GET /healthz`) — для балансировщика и оркестратора.
- **Логи**: все процессы пишут читаемый однострочный текст в stdout через `logging`
  (`app/log.py`, уровень `LOG_LEVEL`) — `docker compose logs -f`. Для внешнего сборщика при
  желании добавить структурный JSON-формат; **метрики** (Prometheus) и readiness-проба пока
  не реализованы.
- **Рейтлимит** на `/api/register` и `/api/login` — настроить на уровне прокси (в
  приложении нет).
- **`user_message`-эхо** идёт durable-лентой `events:{id}` и resumable по `last_event_id`
  (как и токены); за пределами TTL ленты — восстанавливается из Postgres. На масштабе
  распределение не ломает ([07](07-resumable-streams.md), [10](10-hardening.md)).

## Что НЕ требует изменений при масштабировании

- Синхронизация между устройствами/инстансами — уже через Redis (проверено).
- Порядок сообщений в диалоге — гейт по `seq` (работает при любом числе воркеров).
- Идемпотентность обработки — `INSERT … ON CONFLICT` по `message_id` (БД-уровень).
- Восстановление зависших задач — `reclaim_stale` (`XAUTOCLAIM`).
- Resumable-стриминг при реконнекте на другой инстанс — durable-лента + `active_gen`.
- **Пагинация** сообщений и списка чатов — keyset-курсоры на индексах, O(log n + limit)
  без OFFSET, устойчивы к вставкам ([14](14-pagination.md)).
- **Миграции схемы** — раннер с advisory-lock, безопасен при параллельном старте
  инстансов ([13](13-migrations.md)).
