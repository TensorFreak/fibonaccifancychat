# 01. Обзор архитектуры

## Что это

Production-скелет стримингового чат-бота «типа ChatGPT»: вебсокеты, несколько устройств на пользователя, возможность дослать сообщение прямо во время генерации, горизонтальное масштабирование. Стек: **FastAPI + Redis + Postgres + внешний LLM API**.

## Три исполнителя (процесса)

Система намеренно разбита на три независимых процесса. Они не вызывают друг друга напрямую — общаются только через Redis. Это и есть развязка, которая даёт масштабирование и отказоустойчивость.

| Исполнитель | Файл | Роль | К модели ходит? |
|---|---|---|---|
| **api** (FastAPI) | [`app/api/main.py`](../app/api/main.py) | Горячий путь: держит вебсокеты, кладёт вход в очередь, ретранслирует поток в браузер | нет |
| **llm_worker** | [`app/workers/llm_worker.py`](../app/workers/llm_worker.py) | Обрабатывает сообщение: контекст, вызов LLM, сохранение | **да** |
| **summarizer** | [`app/workers/summarizer.py`](../app/workers/summarizer.py) | Сворачивает старую часть диалога в резюме | да (нестримингово) |

Ключевая идея: **api не ходит к модели и не пишет ответы в Postgres**. Он только буферизует вход (`XADD` в очередь) и ретранслирует выход. Вся тяжёлая работа — в воркерах. Поэтому api-инстансы лёгкие и легко масштабируются под число соединений, а воркеры — под нагрузку на модель.

## Хранилища и их роли

| Хранилище | Что лежит | Срок жизни | Роль |
|---|---|---|---|
| **Postgres** | вся история (`messages`), диалоги, `summary` | вечно | source of truth |
| Redis Stream `chat:inbound` | входящие задачи | до `XACK` | durable-очередь api→worker |
| Redis Stream `chat:summarize` | задачи суммаризации | до `XACK` | очередь для summarizer |
| Redis Stream `gen:{id}:{mid}` | токены одной генерации | TTL 5 мин | resumable-лента ответа |
| Redis Pub/Sub `conv:{id}` | control-события (`gen_start`, `user_message`) | не хранится | сигналы во все устройства диалога |
| Redis LIST `ctx:{id}` | горячее окно последних сообщений | TTL 30 мин | быстрый контекст для промпта |
| Redis STRING `sum:{id}` | кэш текущего резюме | TTL 30 мин | быстрый доступ к summary |
| Redis STRING `active_gen:{id}` | id идущей сейчас генерации | TTL 5 мин | догон при реконнекте |
| Redis key `lock:conv:{id}` | замок диалога | TTL 300 c + heartbeat | сериализация сообщений диалога |

Подробная карта ключей — в [09. Модель хранения](09-storage-model.md).

## Сквозной поток одного сообщения

```
Браузер ──ws──▶ api ──XADD──▶ chat:inbound
                                   │
                          xreadgroup (consumer group)
                                   ▼
                              llm_worker
                     ┌─────────────┼───────────────────────────┐
                     │ lock:conv   │ insert_message (Postgres)  │
                     │             │ append ctx:{id}            │
                     │             │ publish user_message ──────┼─▶ conv:{id} (Pub/Sub)
                     │  build_prompt = summary + окно (по бюджету токенов)
                     │             │ publish gen_start ─────────┼─▶ conv:{id}
                     │  stream_completion (LLM) ── токен ──▶ XADD gen:{id}:{mid}
                     └─────────────┼───────────────────────────┘
                                   ▼
                     api: XREAD gen:{id}:{mid} ──ws──▶ Браузер (все устройства)
                                   │
                         каждые N сообщений: XADD chat:summarize ──▶ summarizer
```

Разбор по слоям:

1. **Вход.** Браузер шлёт `{"user_id", "text"}` в вебсокет. api делает `XADD` в `chat:inbound` и сразу свободен — пользователь может слать ещё, не дожидаясь ответа. См. [02. WebSocket API](02-websocket-api.md), [03. Очередь](03-inbound-queue.md).

2. **Захват задачи.** Один из воркеров вычитывает задачу через consumer group (`xreadgroup`). Каждое сообщение достаётся ровно одному воркеру.

3. **Обработка.** Воркер берёт замок диалога, пишет сообщение в Postgres, обновляет горячее окно, эхом публикует `user_message` для других устройств, собирает промпт (резюме + окно по [токен-бюджету](08-token-budget.md)) и идёт к модели. См. [04. LLM-воркер](04-llm-worker.md).

4. **Стриминг ответа.** Каждый токен уходит в durable-ленту `gen:{id}:{mid}`. api-инстансы, где висят сокеты этого диалога, читают ленту и шлют токены в браузеры. Обрыв связи переживается реплеем. См. [07. Resumable streams](07-resumable-streams.md).

5. **Фоновая свёртка.** Раз в N сообщений воркер ставит задачу суммаризатору; тот сжимает старую часть диалога, не блокируя горячий путь. См. [06. Суммаризация](06-summarization.md).

## Масштабирование

- **api** — по числу вебсокет-соединений. Балансировщик раскидывает сокеты по инстансам; связь между инстансами — через Redis (`conv:{id}`, `gen:{id}:{mid}`).
- **llm_worker** — по нагрузке на модель. N копий в одной consumer group `llm-workers` делят входящий поток; каждое сообщение обрабатывается один раз.
- **summarizer** — отдельно, своя группа `summarizers`. Не мешает горячему пути.

Единственная сериализация — **внутри одного диалога** (замок `lock:conv:{id}`), чтобы сообщения не перемешались. Между диалогами всё параллельно.

## Границы и осознанные упрощения

Это скелет. Правки по безопасности/надёжности, внесённые перед корпоративным тестом
(авторизация, владение диалогом, идемпотентность, FIFO-порядок, реклейм PEL, мягкая
остановка, offline-tiktoken), собраны в [10. Харденинг](10-hardening.md). Что осознанно
остаётся простым:

- **Реальный корп-SSO** не реализован — только шов `app/auth.py` (dev-режим). Перед прод-контуром подключить.
- `user_message`-эхо идёт эфемерным Pub/Sub — при обрыве не переигрывается (в отличие от токенов ответа). Восстанавливается перезагрузкой истории из Postgres.
- Один общий inbound-стрим (не шардирован) — на больших объёмах станет горячей точкой (FIFO-порядок при этом уже обеспечен гейтом по `seq`).
- Секреты/TLS (пароли Redis/Postgres, сети) — задача инфраструктуры, не кода.
