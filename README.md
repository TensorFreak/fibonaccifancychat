# Минимальный production-скелет чат-бота (FastAPI + Redis + Postgres + внешний LLM)

Стриминговый чат уровня «типа ChatGPT»: вебсокеты, несколько устройств на пользователя,
дослать сообщение во время генерации, горизонтальное масштабирование.

## Структура

```
chat-backend/
├── docker-compose.yml        # сервисы: postgres, redis, migrate, api, worker, summarizer
├── Dockerfile                # один образ на api, воркеры и раннер миграций
├── migrations/               # SQL-миграции БД (source of truth схемы) — см. docs/13
├── requirements.txt
├── .env.example
├── docs/                     # детальная документация по компонентам (docs/README.md)
└── app/
    ├── config.py             # общие настройки (импортируют И api, И воркеры)
    ├── keys.py               # имена ключей/каналов Redis (единый источник)
    ├── redis_client.py       # async-клиент Redis
    ├── db.py                 # Postgres: сообщения, диалоги, пагинация, резюме
    ├── auth.py               # пароли (bcrypt) и токены (JWT)
    ├── tokens.py             # подсчёт/обрезка токенов (контроль длины промпта)
    ├── migrate.py            # раннер миграций (advisory-lock)

        └── summarizer.py     # фоновый процесс: суммаризация (исполнитель №3)
```

## Гранулярность: что есть что

**Вебсокет** — TCP-соединение между **браузером одного устройства** и **одним процессом
FastAPI** (балансировщик выбирает инстанс). Два устройства пользователя = два сокета,
возможно на разных инстансах. Ключ маршрутизации — `conversation_id`.

**Что хранится где:**

| Хранилище | Что лежит | Срок жизни | Роль |
|---|---|---|---|
| **Redis Stream** `chat:inbound` | входящие задачи `{conversation_id, user_id, message_id, text}` | до XACK | durable-очередь, развязка api↔worker |
| **Redis Stream** `chat:summarize` | задачи суммаризации `{conversation_id}` | до XACK | очередь для исполнителя №3 |
| **Redis STRING** `sum:{id}` | кэш текущего summary | TTL 30 мин | быстрый доступ к резюме для промпта |
| **Redis Pub/Sub** `conv:{id}` | события генерации (`token`, `assistant_start/end`, `user_message`) | не хранится (fire-and-forget) | доставка потока во все устройства диалога |
| **Redis LIST** `ctx:{id}` | горячее окно последних N сообщений | TTL 30 мин | быстрый контекст для сборки промпта |
| **Redis key** `lock:conv:{id}` | замок диалога | TTL 120 c | сериализация сообщений одного диалога |
| **Postgres** | вся история (`messages`), пользователи, диалоги | вечно | source of truth |

## Кто что делает (исполнители)

- **FastAPI (`api`)** — синхронный горячий путь. Принял текст из сокета → `XADD` в стрим.
  Подписан на `conv:{id}` → всё, что публикует воркер, шлёт в сокет. К модели НЕ ходит,
  в Postgres НЕ пишет.
- **LLM-воркер (`worker`)** — фоновый процесс, `python -m app.workers.llm_worker`.
  **Переносит данные** (Redis↔Postgres), **ходит к модели** и **возвращает ответ**
  (публикует токены в Pub/Sub). Масштабируется как N копий в одной consumer group.
  В конце каждого ответа копит счётчик и, набрав порог, ставит задачу в `chat:summarize`.
- **Суммаризатор (`summarizer`)** — фоновый процесс, `python -m app.workers.summarizer`.
  Разбирает `chat:summarize`, сворачивает старую часть диалога в `summary` (Postgres +
  кэш `sum:{id}`). Работает вне горячего пути, ответ юзеру не тормозит.
- **Redis** — сам только удаляет протухшее по TTL. Ничего никуда не «перекладывает».
- **Postgres** — пассивно хранит.

## Как работает память диалога (окно + summary)

Горячее окно `ctx:{id}` держит только последние `ctx_max_messages` сообщений (`ltrim`).
Что старше — выпадает из окна, но лежит в Postgres. Суммаризатор периодически сворачивает
выпавшее в `summary`. Промпт к модели = `[system: summary] + последние N сообщений`
(`build_prompt` в llm_worker). Так окно остаётся коротким, а модель «помнит» суть длинного
диалога. Отметка `conversations.summary_upto` фиксирует, до какого сообщения диалог уже
свёрнут, чтобы не сворачивать одно и то же дважды.

## Поток одного сообщения

```
браузер --ws--> FastAPI(A) --XADD--> Stream chat:inbound
                                          |
                          xreadgroup (consumer group)
                                          v
                                      LLM-воркер
                    persist(user)->PG | append ctx->Redis
                    load ctx (Redis / miss->PG)
                    stream_completion(context)  --> внешний LLM API
                    на каждый токен: PUBLISH conv:{id}
                                          |
   FastAPI(A) и FastAPI(B) подписаны на conv:{id}  <-- Pub/Sub fan-out
        |                         |
   устройство 1              устройство 2   (оба видят стрим)
                    в конце: persist(assistant)->PG | append ctx->Redis
```

## Перекладывание hot↔cold — где именно в коде

- **cold ← hot (запись):** `db.insert_message(...)` в `llm_worker.process` — сразу после
  получения сообщения юзера и после завершения ответа.
- **hot-эвикция:** ничего не делаем руками — `EXPIRE` на `ctx:{id}` (TTL). Данные уже в PG.
- **hot ← cold (регидратация):** `load_context()` — при промахе кэша тянет
  `db.load_recent_messages` и прогревает Redis заново.

## Что осознанно упрощено (следующие шаги к «настоящему проду»)

1. **Надёжность воркера.** При падении до XACK сообщение зависает в PEL. Нужен
   reaper: `XPENDING` + `XAUTOCLAIM` перебирает «застрявшие» и переобрабатывает.
   Плюс идемпотентность по `message_id` (чтобы переобработка не задвоила ответ).
2. **Замок диалога** сейчас блокирует воркер ожиданием (`sleep`). В проде — отдельная
   партиция стрима на диалог или очередь на `conversation_id`, чтобы не занимать воркер.
3. **Суммаризация «на лету».** Реализована базово (см. `summarizer.py`): срабатывает по
   счётчику сообщений. В проде триггер лучше по токенам окна, а не по числу сообщений;
   плюс защита от гонки «ответ читает summary, пока суммаризатор его переписывает»
   (сейчас смягчено кэшем + отметкой `summary_upto`).
4. **Backpressure/отмена:** если юзер закрыл вкладку во время генерации — сейчас воркер
   всё равно догенерирует. Нужен флаг отмены (Redis key) и проверка в цикле токенов.
5. **Аутентификация** вебсокета (токен при `accept`), права на `conversation_id`.
6. **Разделение персистентности** в отдельный worker (как обсуждали): сейчас запись в PG
   делает сам llm_worker — для минимума ок, при росте нагрузки выносится.
